## 技术与原理

### Spark 这类分布式大数据组件，和单机 pandas、PyTorch 在处理数据时有什么不同？

分布式框架把数据和计算切分到多台机器，核心是分区、并行任务与容错重算，适合数据量超出单机内存的批处理与流处理；单机 pandas 适合中小规模快速探索，PyTorch 面向模型训练与推理，用 GPU 加速张量计算。选型看数据规模、时延要求和是否需要迭代训练，很多场景是分布式做预处理和特征、单机或 GPU 做建模的组合。

我的相关经历：我在中文新闻文本分类项目里比较了 TextCNN 和微调 BERT，测试集准确率分别为 0.86 和 0.93；数据预处理、训练脚本和评估由我负责，用验证集选择学习率和训练轮数。这是单机建模的经验，分布式组件我还在学习。

### 一个典型的 ETL 流程包含哪些环节？你会怎么设计分层？

抽取阶段区分全量与增量，增量常用时间戳或变更日志；转换阶段做去重、空值处理、字段标准化和维度关联；装载阶段写入目标表，要保证可重跑且不重复累加。分层通常按贴源层、明细层、汇总层、应用层组织，每层口径清晰。最后加数据校验：行数对账、主键唯一、关键指标比对，发现问题能定位到具体环节。

我的相关经历：我做电商销售数据仓库时，用 SQL 写了从原始订单数据到事实表的清洗和装载脚本，处理了重复订单和缺失的地区字段，装载约 12 万条示例订单数据，脚本可以重复运行。

### 星型模型和雪花模型怎么选？维度建模的关键步骤是什么？

维度建模一般按四步：选业务过程、声明粒度、确定维度、确定事实。星型模型把维度做成单表、允许适度冗余，join 少、查询快、也便于业务理解；雪花模型对维度做规范化，省空间但 join 层数多、使用成本高。数仓面向分析查询时通常优先星型，并保持一致性维度，让不同事实表能按同一口径对齐。

我的相关经历：我设计过一张订单事实表加商品、客户、日期三张维度表的星型模型，围绕订单分析场景组织，下游用 Power BI 出销售看板。

### 做复购、留存这类指标时，SQL 一般怎么写？窗口函数在什么场景下用？

常见做法是先把订单按用户和日期聚合，用 row_number 或 min 取每个用户的首单时间，再判断后续是否在窗口期内再次下单，最后按用户分组统计比例。窗口函数适合做组内排序、去重取最新一条、计算相邻订单间隔。写的时候要注意去重口径、时间边界、NULL 值处理，以及大表上按分区裁剪减少扫描量。

我的相关经历：我在数仓项目里用 SQL 写事实表装载脚本并处理重复订单；看板上的复购率是我写的 DAX 度量，基于事实表数据计算。

### 如果要做自然语言查询数据（NL2SQL），你会怎么设计链路并保证结果可信？

先给模型准确的表结构和字段含义，必要时检索相关表；模型生成 SQL 后做语法与只读校验，只允许查询类语句并限制返回行数；执行报错把错误信息回传让模型重写。结果侧要求同时输出所用 SQL 和返回行数，让用户能复核。可用自建业务问题集衡量一次正确数和纠错后正确数，持续归类失败样例来迭代。

我的相关经历：我用 LangGraph 搭过数据分析 Agent，模型通过查看表结构、执行只读 SQL、生成图表三个工具回答问题；SQL 工具限制只能 SELECT 并限制返回行数，出错回传错误让模型重写。在 30 个自建业务问题上一次正确 24 个，允许一次纠错重试后 27 个。

### 你怎么判断大模型的输出质量是否可信？

先建贴近真实问题的小型评测集，定义可量化的指标，如一次正确数、检索命中率、引用正确率；再让输出可追溯，要求给出引用来源或所用 SQL。工程上限制模型能做的事，比如工具权限和返回规模，降低错误代价。最后对失败样例归类，人工抽检高频场景，把结论反哺到提示、检索和数据质量上。

我的相关经历：数据分析 Agent 我用 30 个自建业务问题测一次正确数和纠错后正确数，并让每个回答附带 SQL、行数和图表文件；RAG 项目里我要求回答列出引用的文章编号，并用 60 条自建问题测检索前 5 命中率。
